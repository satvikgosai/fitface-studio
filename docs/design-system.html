FitFace Studio — design system

The visual reference for :core:ui. Everything below is transcribed from FitFaceTheme.kt and FitFaceComponents.kt; those files are the authority and this page is stale if it disagrees with them. The prose half — why the tokens are shaped this way, and the three places the code knowingly departs from the original design — is in design-system.md beside this file.

This file is self-contained on purpose. No build step, no server, no network: it has to render from a fresh clone on a plane. Do not add a CDN script, a webfont link or an external image to it.

Colour

One teal accent, three semantic hues, and a surface ladder that expresses elevation as lighter surfaces plus a 1dp border — never a shadow. warning and experimental are not part of a Material scheme, so FitFaceTheme provides them through LocalFitFaceSemanticColors; they carry different values per theme because the dark pair is unreadable on a light surface. The ratios below are against that scheme's own background, and SemanticColorContrastTest holds them to 4.5:1.

FitFaceTextColors supplies the two quiet tiers of text, and they are the only way to dim text in this app — there is no alpha to choose at a call site. secondary is meta lines, subtitles and section headings; tertiary is the quietest line where three stack up, as in a project row's name, source and age. Both clear 4.5:1 on every surface in both schemes, which SmallTextContrastTest holds. Disabled controls keep their own alphas and are exempt — a control that cannot be operated should look inert.

Type

Mono is not decoration. In this app the numerals are the content — a coordinate, a byte count, a sequence id — and a proportional digit changes width with its value, so a figure being nudged jitters while you hold the button. Anything quantitative goes in a mono slot. FitFaceType.readout exists because Material's ramp has no mono slot at 20sp, which is why the inspector's coordinates had fallen back to a proportional headlineSmall.

Shape, spacing, elevation

There is no spacing token. A FitFaceSpacing class encoding a 4dp scale used to exist and nothing ever read it, while the UI modules hold ~330 dp literals of which about two thirds are off that scale. It was deleted rather than left to imply a rule the code does not follow — see design-system.md, "Departure 2". The values below are the ones actually in use; treat them as observed, not prescribed.

SHAPE — MaterialTheme.shapes
xs 4 sm 8 md 10 lg 14 xl 18

extraSmall is FitBadge's corner. extraLarge has no consumer, and a few places still hardcode RoundedCornerShape rather than reach for the token.

SURFACE ELEVATION — lighter, not shadow
base low container high

A card is surfaceContainerLow plus a 1dp outlineVariant border. There is no shadow anywhere in the app, and FitFaceElevation was deleted for having no consumers.

Components

Rendered against both schemes, because the semantic colours differ between them and that is exactly where a regression hides. Use the toggle to compare.

These are hand-built approximations, not a pixel-accurate render. The panels are 360px wide to stand in for a 360dp phone, but they draw with whatever sans and mono your browser resolves — Menlo or SF Mono on a Mac, which is materially wider than the Roboto Mono the device uses. Colours, sizes, weights, radii and structure are exact; text widths are not, so do not read a truncation or a fit off this page. The measured device figures are in the width-budget table below, and FitTopBarLayoutTest is what actually holds the line.

Glyphs

There is no icon library in this project and no vector drawable outside the launcher. Every symbol is a text glyph, which both strings.xml headers record as deliberate: they are symbols, not copy, so they stay inline in the Composables where a translator will not see them. A glyph-only control needs a contentDescription — without one a screen reader announces the character, which is how the overflow button used to introduce itself as "midline horizontal ellipsis".

The top bar's width budget

The one component rule with a test attached, because breaking it is invisible. FitTopBar gives its title/subtitle column a weight(1f), so the column is the flexible child and every dp an action takes comes out of the title. A full-label "Report a problem" TextButton took 109dp of a 360dp bar — wider than the title beside it — and the subtitle was silently ellipsized on every editor page, with no exception, no lint warning and nothing in any test.

This is also why the app's three global actions — report a problem, about, check for update — are one ≡ button and a menu rather than three buttons. A DropdownMenu is a Popup, measured in its own window, so the bar pays for the anchor and nothing else: the numbers below are the same as they were for the single button it replaced. FitTopBarLayoutTest.theOpenMenuCostsTheBarNoWidth is what keeps that true.

Two rules follow, and both have been broken here before. An action is a FitIconButton and its label lives in the contentDescription. The always-present action is emitted last, so as the final child its right edge pins to the padding and it stops sliding sideways when a conditional neighbour appears — the library's moved 189px on a tab switch. FitTopBarLayoutTest pins the budget; it asserts geometry rather than whether text was ellipsized, because Robolectric's font metrics are not the device's and a truncation assertion passes while a real phone still clips.

Screens

A page is a distinct task with its own state and its own way out, and earns a back-stack entry. A peek or sheet needs the canvas visible while you use it, or resolves in one tap — a 1px nudge needs the face in the same eyeful, so nudging is never a page. Five rail destinations means one back stack and no nested graphs.
